## 1. Qué es y cómo leerlo

El [modelo entidad-relación](Modelo%20Entidad-Relacion%20PhishGuard.md) define **qué tablas existen y cómo se relacionan**. Este documento define **cómo es exactamente cada campo**.

| Columna | Significado |
|---|---|
| **Campo** | Nombre exacto en PostgreSQL |
| **Tipo** | Tipo de dato y longitud |
| **Nulo** | `No`: obligatorio · `Sí`: opcional |
| **Por defecto** | Valor que asigna la base de datos si no se indica |
| **Clave / Restricción** | PK, FK, UNIQUE, CHECK |
| **Descripción** | Para qué sirve el campo |
| **Ejemplo** | Valor real de muestra |

## 2. Convenciones

| Elemento | Decisión | Motivo |
|---|---|---|
| Nombres | `snake_case`, en inglés, tablas en plural | Estándar en PostgreSQL y Python |
| Identificadores | `UUID` con `gen_random_uuid()` | No revelan cuántos registros hay; compatibles con Supabase Auth |
| Fechas | `TIMESTAMPTZ` | Guarda la zona horaria; evita errores con el horario de verano |
| Texto corto | `VARCHAR(n)` | Limita la longitud de valores controlados |
| Texto largo | `TEXT` | Mensajes, explicaciones, descripciones |
| Datos flexibles | `JSONB` | Metadatos y detalles que varían según el caso |
| Puntuaciones | `INTEGER` de 0 a 100 | Escala única en todo el sistema |
| Valores fijos (estados, tipos) | `VARCHAR` + `CHECK` | Más fácil de modificar con Alembic que un `ENUM` |
| `created_at` | `DEFAULT now()` | Lo rellena la base de datos |
| `updated_at` | `DEFAULT now()` + trigger | Se actualiza solo en cada modificación |

## 4. Identidad

### `auth.users` *(Supabase)*

Tabla interna de Supabase Auth. **No se crea ni se modifica**: guarda el email, las credenciales y las sesiones. PhishGuard solo usa su `id`.

| Campo | Tipo | Descripción |
|---|---|---|
| `id` | `UUID` | Identificador del usuario autenticado |

### `profiles`

Datos de PhishGuard sobre cada usuario: nombre, rol y estado.

| Campo | Tipo | Nulo | Por defecto | Clave / Restricción | Descripción | Ejemplo |
|---|---|:---:|---|---|---|---|
| `id` | `UUID` | No | — | **PK** · **FK** → `auth.users.id` | Mismo identificador que en Supabase Auth | `8b1e…c7` |
| `name` | `VARCHAR(100)` | No | — | `char_length(name) >= 2` | Nombre visible | `María López` |
| `role` | `VARCHAR(10)` | No | `'USER'` | `CHECK` rol | Permisos en la aplicación | `USER` |
| `status` | `VARCHAR(10)` | No | `'ACTIVE'` | `CHECK` estado de usuario | Permite desactivar sin borrar | `ACTIVE` |
| `created_at` | `TIMESTAMPTZ` | No | `now()` | — | Fecha de alta | `2026-11-03 18:40+01` |
| `updated_at` | `TIMESTAMPTZ` | No | `now()` | Trigger | Última modificación | `2026-11-03 18:40+01` |

> El perfil se crea automáticamente al registrarse, con un trigger sobre `auth.users`. El usuario puede cambiar su `name`, pero **no** su `role` ni su `status`.

## 8. Claves foráneas y reglas de borrado

| Tabla.campo | Referencia | Al borrar el padre | Motivo |
|---|---|---|---|
| `profiles.id` | `auth.users.id` | `CASCADE` | Si se elimina la cuenta, se elimina el perfil |
| `analyses.user_id` | `profiles.id` | `CASCADE` | Derecho de supresión: se borran los análisis del usuario |
| `verdicts.analysis_id` | `analyses.id` | `CASCADE` | Sin análisis no hay resultado |
| `verdicts.engine_version_id` | `engine_versions.id` | `RESTRICT` | No se puede borrar una versión con resultados |
| `detected_rules.verdict_id` | `verdicts.id` | `CASCADE` | Las señales dependen del veredicto |
| `detected_rules.engine_version_rule_id` | `engine_version_rules.id` | `RESTRICT` | Protege la trazabilidad histórica |
| `engine_version_rules.engine_version_id` | `engine_versions.id` | `CASCADE` | Borrar una versión en borrador borra su configuración |
| `engine_version_rules.rule_id` | `detection_rules.id` | `RESTRICT` | No se borra una regla en uso |
| `engine_version_thresholds.engine_version_id` | `engine_versions.id` | `CASCADE` | Los umbrales dependen de la versión |
| `lab_campaigns.created_by` | `profiles.id` | `SET NULL` | La campaña se conserva aunque se borre el autor |
| `lab_test_cases.campaign_id` | `lab_campaigns.id` | `CASCADE` | Los casos pertenecen a la campaña |
| `lab_test_runs.test_case_id` | `lab_test_cases.id` | `CASCADE` | Las ejecuciones pertenecen al caso |
| `lab_test_runs.engine_version_id` | `engine_versions.id` | `RESTRICT` | Protege el histórico de pruebas |
| `lab_test_runs.analysis_id` | `analyses.id` | `SET NULL` | La ejecución se conserva como registro |
| `lab_test_runs.verdict_id` | `verdicts.id` | `SET NULL` | Ídem |

> En la práctica, una versión publicada nunca se borra: el `RESTRICT` de `verdicts` lo impide en cuanto tiene un resultado.

## 10. Reglas que valida el backend

Algunas reglas implican varias tablas y no se pueden expresar con un simple `CHECK`. Las valida FastAPI, dentro de la misma transacción:

| Regla | Motivo |
|---|---|
| Los umbrales de una versión no se solapan y cubren de 0 a 100 | Toda puntuación tiene exactamente una clasificación |
| `verdicts.classification` coincide con los umbrales de su versión | Coherencia entre puntuación y nivel |
| `verdicts.engine_version_id` coincide con la versión de las `detected_rules` | Un veredicto solo usa reglas de su propia versión |
| `lab_test_runs.verdict_id` pertenece a `lab_test_runs.analysis_id` | Una prueba no puede mezclar resultados de análisis distintos |
| No se modifica la configuración de una versión `PUBLISHED` | Reproducibilidad de resultados |
| Cada regla activa en la base de datos tiene su clase en Python | Evita que el motor falle por una regla sin implementar |
